2. What's built

Scraper

  • Rightmove search via __NEXT_DATA__ JSON extraction (Next.js page — no BeautifulSoup needed)
  • Deduplicates by Rightmove listing URL; re-scrapes update date_listed and available_from
  • Weekly prices auto-detected via price.frequency == "weekly" and converted to PCM (× 4.3)
  • Uses listingUpdate.listingUpdateDate for "listed date" (not firstVisibleDate, which can be years old for re-listed properties)
  • Move-in date: prefers letAvailableDate from search JSON; daily fallback fetches individual listing pages and extracts from <dt>Let available date</dt>

Travel time calculator

  • TfL Journey Planner API: 12 calls per listing (3 destinations × 4 modes)
  • 5 listings processed in parallel; all 12 calls within each listing run concurrently
  • Global rate limiter at 7 calls/sec across all threads (safely under 500/min cap)
  • Fallback: if transit_no_bus returns null, uses transit_all for the 30-min threshold check
  • Failed listings (all transit times null — TfL API glitch) have their rows cleared and are automatically retried on the next pass

Dashboard

  • Card grid, 30 per page, with pagination
  • Default sort: Best match (composite score — see §5)
  • Also sortable by: best commute, cheapest first
  • Status filter: hide rejected / shortlisted only
  • Header stats: N listings match · N commute · N too late · N calculating
  • Per-card: photo, price, beds, area, listed-N-days-ago, available-from date, 3×4 travel time table, Shortlist / Reject / View buttons
  • Travel time pills: green (<20 min) / amber (20–30) / red (>30)
  • Green "New" badge on photo for listings ≤ 2 days old
  • Available-from shown in green (ideal window) or amber (acceptable)

Background jobs (APScheduler)

JobFrequencyWhat it does
Scrape + travel timesHourlyFetches new Rightmove listings, calculates TfL times for any new ones
Daily listing checkEvery 24 hrsFetches each active listing page; marks removed ones; fills missing available-from dates

Data flow

  1. Hourly scraper hits Rightmove search (newest-first, up to 1,000 results), saves new listings to SQLite
  2. Travel time worker picks up listings with no times, fires 12 concurrent TfL API calls per listing across 5 parallel workers
  3. Daily check fetches individual listing pages: marks removed, fills missing available-from dates
  4. Flask serves the dashboard from SQLite — filters, scores, paginates in Python, renders Jinja2 template

5. Scoring algorithm

Lower score = better. Used for "Best match" sort order.

score = (worst_work_commute × 2)
      + (price_norm × 8)       # price_norm = (price - 2500) / 800, range 0–1
      + bed_penalty            # +15 if only 2 bedrooms
      + avail_penalty          # 0 if ideal window, up to +10 approaching cutoff

Component weights rationale

ComponentWeightEquivalent to…
Commute (mins)×2 per minute20-min commute scores 40 pts
Price×8 across £800 range£3,300 vs £2,500 = 8 pts penalty
2-bed vs 3-bed+15 flat penalty≈ 7.5 extra commute minutes
Availability+0 to +10≈ 5 extra commute minutes at worst

worst_work_commute = max(transit_no_bus to work, transit_no_bus to LISA). Falls back to transit_all if TfL can't route without buses.

Listings with no calculated times are hidden until TfL calls complete. Listings where commute > 30 min or available_from > 49 days out are filtered before scoring.

6. Background jobs

Hourly scrape + travel times

  1. Fetch Rightmove search pages (newest-first, cap 1,000 results, 2s between pages)
  2. Upsert listings — new ones inserted, existing ones get date_listed and available_from refreshed
  3. Clear any listings where all transit times are null (TfL glitch) — queues them for retry
  4. Run travel time calculator: 5 concurrent workers, 12 parallel TfL calls per listing, global 7 req/sec rate limiter

Daily listing check

  1. Fetch every active listing's Rightmove page (0.4s sleep between requests)
  2. If "removed by agent" banner found → set is_removed = 1
  3. If available_from is null → extract from <dt>Let available date</dt> in the HTML

~1,200 listings × 1.4s ≈ 28 min per daily run. Runs as a daemon thread so the dashboard stays responsive throughout.

8. Running the app

conda activate london_flat_hunting
python main.py

Flask starts immediately at http://localhost:5000. The scraper and travel time calculator run in background threads — new listings appear as you refresh.

First run behaviour

  • Scraper fetches ~1,000 Rightmove listings (~3 min with 2s page delays)
  • Travel time calculator works through them in parallel (~20–25 min for full batch)
  • Dashboard shows qualifying listings as they complete — refreshes show more appearing
  • Daily check runs after 24 hrs to catch removals and fill missing dates

9. Roadmap

Recommended order: Map (next, ~2 hrs, adds value locally now) → Multi-user voting (~3 hrs) → Cloud deploy (~1 hr). All three work identically once deployed to Railway.
A
Map view Next up

Interactive map tab alongside the card grid. Leaflet.js (free, CDN, no API key).

Features

  • Colour-coded pins (green/amber/red = same commute scale as cards)
  • Click pin → popup: price, beds, worst commute, available-from, View link
  • Layer toggles: all qualifying / shortlisted only / show rejected
  • Marker clustering at city scale (Leaflet.markercluster)
  • Optional: 30-min isochrone overlays around Old Street and LISA using TravelTime API (free tier) — stored as GeoJSON, fetched once

Implementation plan

  • New Flask route /map with a full-page Leaflet template
  • New API endpoint /api/listings.json — returns all qualifying listings as GeoJSON features
  • Isochrones (if added): one-time fetch from TravelTime API, stored in a geojson DB table, served from /api/isochrones.json

Effort: ~2 hrs without isochrones, ~3 hrs with.

B
Multi-user voting & comments After map

Lightweight collaboration for flatmate decision-making. No passwords — name picker stored in a cookie.

Schema additions

TableColumns
voteslisting_id, user_name, status (shortlisted/rejected/new), created_at
commentslisting_id, user_name, body, created_at

UI changes

  • "Who are you?" modal on first visit — name stored in cookie
  • Shortlist/Reject buttons become per-user; vote summary shown on each card: Nik ✓ · Sam ? · Alex ✗
  • Filter: "only listings everyone shortlisted"
  • Collapsible comment thread under each card

Effort: ~3 hrs.

C
Cloud deployment (Railway) After voting

Deploy to Railway: ~$5/month, persistent SQLite volume, one-command deploy.

Steps

  1. Add Procfile: web: python main.py
  2. Add runtime.txt: python-3.12
  3. Push repo to GitHub, connect to Railway
  4. Set TFL_API_KEY env var in Railway dashboard
  5. Share URL with flatmates
Scraping from cloud IPs: Rightmove sometimes blocks cloud provider IP ranges. Mitigation: run the scraper locally (Mac) and push to a POST /ingest endpoint on Railway — only the dashboard and travel time calls live in the cloud.
SQLite concurrency: Fine for 3–4 concurrent users. If write-locking becomes an issue, Railway has a one-click Postgres add-on; the code change is a small swap.

Effort: ~1 hr.

Further future ideas

  • Zoopla integration — second scraping source, same pipeline
  • Telegram/email alerts — push notification when a new listing passes all filters
  • Price history — track when an agent reduces the asking rent
  • Google Maps Routes API — drop-in for TfL if faster bulk recalculation ever needed (~$5–6 one-time; 4 min vs 26 min for initial bulk)
