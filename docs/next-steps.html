Making the app shareable and collaborative

Recommended order: Comments & voting first (makes cloud worth it) → then cloud deploy (one-command). Both are independent of each other and can be done in any order, but deploying before adding comments means your girlfriend sees a read-only app with no way to interact.

1 — Multi-user comments & voting ~3 hrs

No login, no passwords. Each person picks their name on first visit — stored in a browser cookie. The system tracks per-person votes and comments independently.

New DB tables

TableColumnsNotes
votes listing_id, user_name, status (shortlisted/rejected/new), created_at One row per person per listing. Replaces the current global status field on listings.
comments listing_id, user_name, body, created_at Free-text comments. Multiple per person per listing.
The current listings.status column is global (one status for the whole app). Once voting is added, status becomes per-user. Migrate existing shortlisted/rejected entries into votes during the schema change, then drop/ignore listings.status.

Name picker

On first visit, a modal asks "Who are you?" with a fixed set of names (e.g. Nik, [girlfriend], [flatmate 1], [flatmate 2]). The chosen name is stored in localStorage or a cookie. No server-side session needed — just a plain string sent with each vote/comment request.

Names are hardcoded in a FLATMATES list in config.py — easy to update.

Dashboard changes

  • Shortlist/Reject buttons become per-user — current user's action is shown highlighted
  • Vote summary row on each card: Nik ✓   Alex ?   Sam ✗
  • Filter: "Show only listings everyone shortlisted" (useful for final decision)
  • Collapsible comment thread beneath each card — shows existing comments + a text input to add one

Map changes

  • Popup shows vote summary (who voted what) and last 2 comments
  • Vote buttons in popup work the same as on cards

New API endpoints needed

# Vote on a listing (replaces current /action/)
POST /vote/<listing_id>
Body: { "user": "Nik", "status": "shortlisted" }

# Add a comment
POST /comment/<listing_id>
Body: { "user": "Nik", "body": "Love the roof terrace!" }

# Get comments for a listing (used by popup)
GET /comments/<listing_id>

2 — Cloud deployment (Railway) ~1 hr

Deploy to Railway: Python/Flask native, persistent volume for SQLite, ~$5/month, URL assigned automatically.

Steps

1
Initialise a git repo in the project folder if you haven't: git init && git add . && git commit -m "initial"
2
Push to a GitHub repo (can be private)
3
Create Procfile in the project root: web: python main.py
4
Go to railway.app → New Project → Deploy from GitHub repo
5
In Railway settings → Variables, add TFL_API_KEY
6
Add a Volume in Railway and set mount path to /app/data so the SQLite DB persists across deploys
7
Railway assigns a public URL like flat-hunter.up.railway.app — share this with your flatmates

Sending the existing DB to the cloud

Once Railway is set up, upload your local data/listings.db to the Railway volume so you don't start from scratch (all existing listings, travel times, shortlists carry over).

# Install Railway CLI
npm install -g @railway/cli

# Upload local DB to volume
railway run --service flat-hunter -- cp data/listings.db /app/data/listings.db
Rightmove + cloud IPs: Rightmove sometimes blocks requests from cloud provider IPs. Test by checking the scraper logs after deploy. If it fails, keep the scraper running locally and only host the dashboard on Railway — the scraper pushes new listings via a POST /ingest endpoint (easy to add). TfL API calls are fine from cloud.
SQLite concurrency: Fine for 3–4 users. If you see database-locked errors, Railway has a one-click Postgres add-on — swap sqlite3 for psycopg2 in db/database.py.

Sharing access

The Railway URL is public by default. For a bit of protection without full auth, you can add a simple secret URL path — e.g. /secret-flatmates-only/ that sets a cookie allowing access. This takes ~30 mins and keeps the app private without building a full login system.

Alternatively, Railway supports Private Networking with a one-click toggle, but that requires everyone to be on the same Railway team.

Doing both together

The cleanest sequence:

  1. Build comments/voting locally (easier to iterate)
  2. Test with 2–3 people using localhost to check the UX
  3. Deploy to Railway
  4. Upload existing DB
  5. Share URL with flatmates

Total effort: roughly one focused afternoon.
